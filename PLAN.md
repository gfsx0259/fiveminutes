# Rider

Мультиорганизационный Lead Market рядом с текущим LM. Текущий контур seq не переписываем. Бизнес-схема зафиксирована в `BUSINESS.md`: байер выставляет слот, партнёр его принимает, сделка не выходит за организацию. Закрытый стенд на отдельной тачке описан в `INFRA.md`. Код пишется по `CONVENTIONS.md`.

LM сейчас заточен под одну компанию: внутренние байеры и афф-отдел, который в admin собирает заявки партнёров. Rider возвращает исходную схему. Байер сам поставляет лиды, партнёр сам их покупает. Платформа заводит сколько угодно таких организаций. Правило наценки записано в `BUSINESS.md`.

## Домены

```text
owner.rider.io
    заводит организацию и её апекс

chase.io
    id.chase.io
    buyer.chase.io
    partner.chase.io
    api.chase.io

marshall.io
    id.marshall.io
    buyer.marshall.io
    partner.marshall.io
    api.marshall.io
```

Отдельный `admin.<apex>` в первой версии не делаем. Корень дерева байеров приглашает байеров и партнёров и настраивает структуру. Owner в лиды организации не входит.

## Поток лида

```text
ключ байера
    -> POST /v1/lead организация определяется ключом, лид проверяется здесь же
    -> matcher       только заказы этой организации
    -> integration   коннектор, который партнёр выбрал из каталога
    -> CRM партнёра
```

## Деньги

Правило наценки, момент списания и возврат записаны в `BUSINESS.md`. Пополнение кошелька партнёра в USDT. Провайдер выбираем до реализации кошелька.

## Чем не является текущий LM

| | LM сейчас | Rider |
| --- | --- | --- |
| Партнёров заводит | афф-отдел в admin | корень байеров, инвайтом |
| Лиды приходят | от внутренних байеров | от байера по его ключу |
| Покупка | заказы собирает admin | партнёр принимает слот байера или создаёт demand |
| Домен | один апекс, роли admin / buyer / partner | свой апекс на организацию |
| CRM | ведёт платформа | партнёр выбирает коннектор и вводит креды |
| Деньги | цена внутри компании | кошелёк партнёра и наценка платформы |

Кабинет сейчас режется первой меткой хоста (`admin`, `buyer`, `partner`), и роль обязана с ней совпасть. Для `buyer.chase.io` та же схема подходит: метка это роль, апекс это организация. `owner.rider.io` добавляет роль owner.

## Kratos

Один процесс и одна база идентичностей на все организации.

Self-hosted Kratos держит один public base URL и один `session.cookie.domain`. Сейчас это `leadmarket.io`, плюс статические CORS и return URL. Кука одного апекса не читается на другом, и так и должно быть: сессия chase не является сессией marshall.

Как оставляем один API:

- `id.chase.io` и `id.marshall.io` проксируются на один Kratos.
- В конфиге домен куки пустой.
- Край по Host запроса выставляет `Domain` у сессионной и csrf-куки на апекс (`chase.io` или `marshall.io`). Тогда buyer, partner и api этого апекса видят сессию.
- При создании организации owner дописывает origins кабинетов в CORS и allowed return URL и перечитывает конфиг. Это редкая операция.
- API живёт на `api.<apex>`, чтобы браузерная кука доезжала так же, как сейчас до `api.leadmarket.io`. Организация берётся из Host, не из тела запроса.
- Ключ байера на receiver к сессии Kratos не относится.

Отдельного `worker-validator` и отдельного receiver нет. Проверка лида синхронная и происходит в API на `POST /v1/lead`, до записи в ClickHouse.

## Состав `meta/rider`

| Папка | Зачем |
| --- | --- |
| `matcher` | лид байера на принятый слот или demand той же организации |
| `integration` | каталог CRM, креды партнёра, доставка |
| `infra` | ClickHouse, Postgres, Redis |
| `api` | Yii 3, как LM API: приём лида, кабинеты, кошельки, комиссия, организации |
| `dashboard` | Vue 3, Pinia, Vuetify: owner, buyer, partner |
| `kratos` | один API и UI логина на `id.<apex>` |

## Порядок

1. Организация, апекс, край Kratos.
2. Ключ байера, приём и проверка в API, matcher внутри организации.
3. Кошелёк партнёра и наценка.
4. Каталог CRM и креды партнёра.
5. Кабинеты buyer и partner. Дерево байеров и demand.

До кошелька нужно зафиксировать провайдера USDT и выбрать правило наценки из `BUSINESS.md`.
